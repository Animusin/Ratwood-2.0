# Донатерские дома: инструкция по подключению

Для программиста или администратора сервера Ratwood-2.0. Реализация находится
в [PR #173](https://github.com/Animusin/Ratwood-2.0/pull/173), пока это прототип
для контролируемого тестирования. Доступ владельца репозитория к БД не требуется:
описанные действия выполняет специалист с доступом к серверу и игровой БД.

Нужно установить код PR, создать одну таблицу в **игровой** MySQL/MariaDB-базе,
проверить существующее подключение к БД подписок и включить конфигурационный флаг.
Автоматической миграции при запуске сервера нет.

## 1. Подготовка

Используйте тестовый экземпляр сервера с отдельной игровой БД или согласованный
тестовый раунд. Перед изменением рабочей БД сделайте её резервную копию обычным
способом, принятым на сервере.

Получите код PR #173 и соберите `roguetown.dme` принятым в проекте способом.
В сборке должны присутствовать `code/modules/supporter_housing/`, а при
развёртывании — все три файла из `_maps/supporter_housing/`. Они загружаются
во время игры, поэтому одной обновлённой `.dmb` без файлов шаблонов недостаточно.

В действующей конфигурации сервера проверьте следующие параметры. Их объявления
находятся в `code/controllers/configuration/entries/dbconfig.dm`.

| Параметры | Назначение |
|---|---|
| `SQL_ENABLED` | Включает SQL; необходим и для домов, и для проверки подписок. |
| `ADDRESS`, `PORT`, `FEEDBACK_DATABASE` | Адрес, порт и имя **игровой** БД. |
| `FEEDBACK_LOGIN`, `FEEDBACK_PASSWORD` | Учётная запись игрового сервера в этой БД. |
| `FEEDBACK_TABLEPREFIX` | Префикс таблиц игровой БД; может быть пустым. |
| `DONATIONS_ENABLED` | Включает существующую систему подписок. |
| `DONATION_ADDRESS`, `DONATION_PORT`, `DONATION_DATABASE`, `DONATION_LOGIN`, `DONATION_PASSWORD` | Существующее отдельное подключение к БД подписок. |

Проверяйте фактически загружаемую конфигурацию, включая подключённые файлы.
Примерная конфигурация из репозитория не заменяет конфигурацию работающего сервера.
Используйте уже настроенные подключения; для домов новая отдельная БД не нужна.
Если стандартная игровая БД ещё не настроена, сначала настройте её обычным
способом: миграция домов не создаёт остальные игровые таблицы.

## 2. Создание таблицы

Подключитесь к базе из `FEEDBACK_DATABASE` учётной записью с правом `CREATE`.
Например, из корня репозитория откройте SQL-клиент:

```text
mysql -h HOST -P PORT -u MIGRATION_USER -p GAME_DB
```

Замените `HOST`, `PORT`, `MIGRATION_USER`, `GAME_DB` действующими значениями.
Пароль клиент запросит отдельно. Можно использовать клиент `mariadb` или
административный интерфейс БД и выполнить в нём SQL-файл.

Проверьте выбранную базу:

```sql
SELECT DATABASE();
```

Если `FEEDBACK_TABLEPREFIX` пустой, выполните
[`SQL/supporter_housing.sql`](../SQL/supporter_housing.sql):

```sql
SOURCE SQL/supporter_housing.sql;
SHOW CREATE TABLE `supporter_housing`;
```

Если префикс задан, сначала сделайте копию миграции и замените в ней имя таблицы
на **точное значение префикса + `supporter_housing`**. Например, при
`FEEDBACK_TABLEPREFIX tg_` имя должно быть `tg_supporter_housing`.
Разделитель автоматически не добавляется. Выполните изменённую копию SQL
в игровой БД и проверьте `SHOW CREATE TABLE` с получившимся именем.
В коде тот же префикс добавляется функцией `format_table_name()`.

Ожидаемая структура:

| Поле | Тип и назначение |
|---|---|
| `ckey` | `varchar(32)`, первичный ключ: нормализованный BYOND-аккаунт владельца. |
| `revision` | `int unsigned`, версия успешного сохранения. |
| `decor` | `text`, JSON с разрешёнными предметами, относительными координатами, изменениями стен и архивом. |
| `updated_at` | `timestamp`, время последнего сохранения. |

Таблица использует InnoDB и utf8mb4. Миграция содержит
`CREATE TABLE IF NOT EXISTS`: повторный запуск не стирает сохранения, но также
не исправляет структуру уже существующей таблицы. При несовпадении структуры
сначала выясните её происхождение и подготовьте отдельную миграцию с резервной копией.

Учётной записи из `FEEDBACK_LOGIN` нужны права **SELECT, INSERT, UPDATE** на
получившуюся таблицу. Для работы домов не нужны `DELETE`, `DROP`, `ALTER` или
постоянное право `CREATE`. Если права уже выданы на всю игровую БД, дополнительных
разрешений может не потребоваться; проверьте их под серверной учётной записью.

Эта миграция не меняет `schema_revision` и таблицы подписок. Не импортируйте
полную `tgstation_schema*.sql` поверх существующей БД ради подключения домов.

## 3. Включение

После создания таблицы добавьте отдельную строку в действующий `config/config.txt`
либо в реально подключаемый конфигурационный файл:

```text
SUPPORTER_HOUSING
```

Это флаг без значения `1`. Загрузите обновлённую сборку и конфигурацию при
плановом запуске нового раунда/экземпляра сервера. По умолчанию флаг отсутствует
и функция выключена.

Проверьте в журналах успешное подключение к игровой и донатерской БД и отсутствие
SQL-ошибок о таблице или правах. Для домов поддержаны Rockhill, Desert Town и
Dun World. Действующая подписка проверяется существующей системой; допустимые
значения уровня — `wizard`, `cultist`, `assistant`.

## 4. Проверка в игре и БД

1. Зайдите тестовым аккаунтом с подтверждённой подпиской за Towner, другую
   городскую профессию, Mercenary или Adventurer. У явной антагонистической роли
   вроде Bandit или Wretch новый дом создаваться не должен.
2. До получения другого ключа через жилую дверь выберите свободный обычный дом
   тавнера. Подтвердите стандартный вопрос о своём доме, получите ключ и примените
   его к двери. Сохраняется исходное ограничение на одну выдачу жилого ключа.
   Профессиональные мастерские и двери бани не являются входами в донатерский дом.
3. Открытие занимает пять прерываемых секунд; переход — ещё пять. Убедитесь,
   что загрузился нужный размер дома, внутренний замок открывается полученным
   ключом, а выход доступен без подписки и даже при закрытой внешней двери.
4. Расставьте несколько разрешённых предметов в узнаваемых местах, измените
   обычную стену или дверь. Позвоните в колокол сохранения и подтвердите действие.
   Проверяйте вне пожара/боя; между попытками сохранения нужна минута.
5. После сообщения об успешном сохранении выполните в игровой БД запрос ниже.
   При префиксе замените имя таблицы. Вместо `testaccount` укажите реальный
   нормализованный `ckey` тестового аккаунта.

```sql
SELECT `ckey`, `revision`, `updated_at`, OCTET_LENGTH(`decor`) AS json_bytes
FROM `supporter_housing`
WHERE `ckey` = 'testaccount';
```

   После первого сохранения ожидается одна строка с `revision = 1`.
   После следующего успешного сохранения версия должна увеличиться на один.
   Для проверки записей можно отдельно прочитать `decor`: `x`/`y` считаются от
   участка дома, записей абсолютного Z-положения дома в этом JSON нет.
6. Начните **новый раунд**, зайдите тем же аккаунтом, заново выберите свободный
   вход и откройте дом. Проверьте положение мебели, стен и дверей. Повторный вход
   в тот же дом в текущем раунде не проверяет загрузку сохранения из БД.
7. На тестовом контуре проверьте понижение подписки: не подходящие по уровню или
   размеру предметы остаются в архиве, а при последующем повышении пытаются
   восстановиться. Изменение подписки не перестраивает уже открытый дом в раунде.
8. Проверьте истечение подписки и недоступность каждой БД на тестовом контуре:
   новый дом/сохранение должны отклоняться без удаления предыдущей записи.
   Уже открытый дом и выход из него остаются доступны до конца раунда.

Колокол сохраняет только явно подтверждённую обстановку. Автосохранения в конце
раунда нет. Содержимое сундуков/бочек, жидкости, топливо, незаконченная продукция,
мобы и произвольные свойства объектов не сохраняются. Восстановленная обстановка
имеет нулевую продажную стоимость и не выдаёт материалы при разборке.

## 5. Если что-то не работает

| Симптом | Что проверить |
|---|---|
| Не найден флаг конфигурации | Загружена ли сборка PR и правильный файл конфигурации. |
| `Table ... doesn't exist` | Правильную игровую БД, исполнение миграции и `FEEDBACK_TABLEPREFIX`. |
| `Access denied` / запрет записи | Подключение и права серверной учётной записи на таблицу. |
| Проверка подписки недоступна | `SQL_ENABLED`, `DONATIONS_ENABLED`, параметры и доступность существующей донатерской БД. |
| Не выдаётся жилой ключ | Разрешённую роль/подписку, свободную обычную дверь, не был ли уже выдан ключ через другую жилую дверь. |
| Вход не создаёт дом | Флаг, карту, владельца ключа/двери, роль, подписку, доступность игровой БД и файлы шаблонов. |
| Колокол отклоняет сохранение | Владельца, роль/подписку, близость к колоколу, пожар/бой, минутный интервал и лимиты обстановки. |
| Ошибка версии сохранения | Другой экземпляр сервера мог сохранить тот же аккаунт; запись защищена от перезаписи устаревшей версией. Не обнуляйте `revision`. |

Битая/неподдерживаемая запись не заменяется пустым домом автоматически.
При разборе такой проблемы сначала сохраните копию строки; не удаляйте её для
«исправления» без отдельного решения о судьбе вещей владельца.

## 6. Отключение и границы проверки

Чтобы выключить функцию, уберите или закомментируйте `SUPPORTER_HOUSING` и
запустите новый раунд/экземпляр с обновлённой конфигурацией. Таблицу оставьте:
она сохраняет данные для будущего включения. Не используйте `DROP`/`TRUNCATE`
как способ отключения. Не рассчитывайте, что изменение флага посреди текущего
раунда удалит уже загруженные дома или отменит их работу.

Локально выполнены 671 проверка без ошибок и полная сборка BYOND 516.1687 без
ошибок/предупреждений. SQL-транспорт в тестах был подменён; реальное подключение
БД и клиентские окна подтверждения ещё нужно проверить по шагам выше.
Отдельный тест загрузил 60 домов с примерно 7000 простыми предметами за 11,21 с,
пиковая память всего процесса — 678 МиБ. Это не проверка 60 подключённых игроков,
одновременного производства, массовых пожаров и освещения.

На картах сейчас 25/26/33 подходящие обычные двери соответственно. На отдельном
Z есть место для 60 участков, но для 60 независимых входов потребуется работа
картографа. Размеры, лимиты и полный формат сохранения описаны в
[`code/modules/supporter_housing/README.md`](../code/modules/supporter_housing/README.md).
